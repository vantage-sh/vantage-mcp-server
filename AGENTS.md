# AGENTS.md

Working notes for agents in this repo. The README covers setup and deployment; this file lists the traps that are not obvious from a quick file scan.

**This file is not a recipe.** Step-by-step instructions live in the skills and subsystem READMEs linked below. Do not reconstruct conventions from neighboring files — much of the existing code predates current conventions.

Leave unrelated convention drift alone. Fixing it belongs in a separate PR.

## How tools plug in

Every tool file's default export is a `registerTool({...})` call (`src/tools/structure/registerTool.ts`). Tools become live by being **imported** — that is all `src/tools/index.ts` does. The index is generated by `npm run generate-tools-index`; `test/tools/index.test.ts` fails CI if it is stale.

New tools go under `src/tools/<resource>/`, not at the top level of `src/tools/`, and must ship with a matching unit test under `test/` (`testTool`). Add `import "./<verb>-<resource>";` to the resource's `index.ts`, then run `npm run generate-tools-index`. Never hand-edit `src/tools/index.ts`.

Also generated — never hand-edit: `src/resources/index.ts` (`npm run generate-resources-index`), `worker-configuration.d.ts` (`npm run cf-typegen`).

Useful examples to copy:

- Nested tool family: `src/tools/budgets/`, `src/tools/cost-reports/`
- Another nested family with shared request typing: `src/tools/recommendation-views/`
- Delete tool and 204 behavior: `src/tools/folders/delete-folder.ts`

## Invariants

These are easy to violate by copying a neighbor. The skills show the full patterns; this is the checklist.

- **URL path tokens use `pathEncode`.** Any token interpolated into a Vantage API path goes through `pathEncode` from `@vantage-sh/vantage-client`. See `folders/delete-folder.ts`, `teams/get-team.ts`.
- **`callVantageApi` returns a discriminated union.** `{ ok: true, data }` or `{ ok: false, errors }`. Check `response.ok` and throw `MCPUserError` with the errors. Do not try/catch around the call — `registerTool` handles translation.
- **204 No Content** is normalized in `src/shared.ts` to `{ ok: true, data: undefined }`. Delete tools must not touch `response.data`.
- **Delete tools return `{ token: args.<resource>_token }`.** Confirms what was deleted without leaking anything. See `folders/delete-folder.ts`.
- **`MCPUserError` constructor takes a plain object.** `new MCPUserError({ errors: response.errors })` for upstream failures; `new MCPUserError({ errors: [{ message: "..." }] })` for cross-field validation. Do not pass an `Error`.
- **Vantage client types are the source of truth** for request/response shape (`RequestBodyForPathAndMethod` / `ResponseBodyForPathAndMethod` from `@vantage-sh/vantage-client`). When the zod-inferred type does not line up, cast at the `callVantageApi` site — see `recommendation-views/create-recommendation-view.ts`, `cost-reports/create-cost-report.ts`, `cost-providers/get-cost-provider-accounts.ts`.

## Verification before PR

**CI runs** (`.github/workflows/test.yml`): TypeScript check, Biome lint, Vitest (with coverage), commitlint on non-`main` branches except Dependabot. Evals and end-to-end verification are **not** in CI.

**Pre-commit** (`.husky/pre-commit`): `npm run check:lint:all -- --write` (Biome with autofix).

### Repository checks

- If you touched tool layout: run `npm run generate-tools-index`.
- If you touched resources: follow [src/resources/README.md](src/resources/README.md) and run `npm run generate-resources-index`.
- If you changed Worker bindings: run `npm run cf-typegen`.
- Run `npm run type-check`, `npm run lint`, and `npm test -- --run`. Vitest also asserts that the tool and resource indexes are current.

The default TypeScript and Biome checks exclude `.agents/`; validate changed scripts directly and report any runtime verification that was not performed.

### Surfacing verification findings in chat

- When verification reveals a product failure or a mismatch between advertised tool behavior and the real API, clearly surface the unresolved gap in the agent chat when discovered. A note in a local report or PR description is not sufficient, even when the issue predates the current change.
- Explain the input or action that failed, the observed result, the user-visible impact, and what still needs fixing or verification. Distinguish an incorrect test harness from a product defect.
- If a workaround changes the request or narrows coverage, state what the successful retry proves and what remains broken or unverified. Passing after removing the failing input does not validate the original behavior.
- Repeat unresolved product gaps in the final handoff, with a concrete next step. Keep detailed diagnostics in the local report and apply the PR guidance below separately; omitting an unrelated issue from a public PR must not hide it from the user.

### Writing verification in a PR

- Use short, easy-to-read bullet points. Each behavior bullet should say what was validated, how it was exercised, and what was observed. For example: "Validated moving a Dashboard by moving it between Folders and to root, then reading it back to confirm its location and preserved widgets."
- Describe the behaviors checked; aggregate check counts alone do not explain coverage. Summarize automated checks with their commands and results in separate bullets.
- Include relevant conditions and gaps, such as using a real API instead of mocks, testing only with account-owner access, or authoring evals without executing them. Mention failures or workarounds when they limit confidence in the submitted change.
- Keep the full run history and evidence in the local verification report. Public PR descriptions must not reference local files, run directories, local checkouts, private dependency commit hashes, or source-hash bookkeeping. Omit resolved harness mistakes, unrelated existing bugs, and routine process/credential cleanup details; report cleanup only when something remains or affects review.
- Link evidence only when PR readers can access it, such as a CI run or a repository file. Include a tested commit or deployment identifier only when needed to distinguish the verified revision from the current PR.

### Evals (opt-in)

When adding or changing a tool, ask whether the user wants evals included. If so, confirm that the selected provider's API key is configured in the ignored `.env` file and follow [.agents/skills/writing-evals/SKILL.md](.agents/skills/writing-evals/SKILL.md). Do not backfill or update evals unless requested.

Authoring an eval does not authorize model-backed execution. Run it only with explicit approval for the selected tools and model and confirmation of credential setup. Without that approval or setup, author the case only and report the pending run. After an authorized run, commit the resulting JSON under `evals/results/<model>/<resource>/`; use `npm run eval:site` to inspect the report locally.

### End-to-end verification (opt-in)

When work is complete, ask whether the user wants to run end-to-end verification. If so, follow [.agents/skills/verify-vantage-mcp/SKILL.md](.agents/skills/verify-vantage-mcp/SKILL.md).

- The [feature map](.agents/skills/verify-vantage-mcp/features/README.md) covers local OAuth discovery and consent, hosted tool calls, local stdio, and staging login. Update the matching feature file when changing a user-visible path.
- Local OAuth verification stops at the consent screen. Successful tool calls need Core and a token it accepts; full Auth0 login needs staging. Each staging deploy requires explicit approval, and staging must be restored to `main` afterwards.
- Keep evidence under the ignored `tmp/verify-vantage-mcp/` directory. Record tested commits, entry points, results, artifact paths, skipped paths, and unmet prerequisites in the local verification report and handoff. Summarize relevant outcomes in the PR using the guidance above; passing unit tests or tool listing alone does not prove a successful authenticated tool call.
- Clean up every local run, including failed attempts, using the skill's cleanup command. Stop only processes started by that run and preserve its evidence.
